# Issue #3475 — Inconsistent usage of ag_ui_thread_id vs agui_thread_id

- Repo: microsoft/agent-framework · [issue #3475](https://github.com/microsoft/agent-framework/issues/3475)
- Category: **Integration-pkg — gap (audit; low severity)**

## Summary
The in-tree MAF implementation used two different `ChatOptions.AdditionalProperties` keys for
the thread id (`ag_ui_thread_id` and `agui_thread_id`), so producers and consumers could miss
each other.

## Finding (our SDK)
Our client centralizes the key in a single constant and uses it consistently:
`AGUIClientInternalKeys.ThreadId == "agui_thread_id"`
(`src/AGUI.Client/Internal/AGUIClientInternalKeys.cs:16`). Our hosting layer does not surface a
separate thread-id key at all — it stashes the whole `RunAgentInput` under
`AGUIConstants.RunAgentInputKey` (`agui_input`) — so there is no `ag_ui_*`/`agui_*` divergence
on our side.

## Validation
No automated test added: `AGUIClientInternalKeys` is `internal` and not visible to the test
project, and the property is exercised indirectly by the existing client tests. The contract
is verified by the single-constant source above — **note/audit only**.

## Proposed step (not implemented)
When MAF consumes our packages, standardize on our single `agui_thread_id` key (drop the
`ag_ui_thread_id` variant). Optionally expose the key name as a public constant if MAF needs
to read it directly.
