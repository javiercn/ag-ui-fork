# Issue #3723 — OpenTelemetry not emitted when Agent triggered through AGUI

- Repo: microsoft/agent-framework · [issue #3723](https://github.com/microsoft/agent-framework/issues/3723)
- Category: **Mostly AF-specific + distributed-tracing/config — ⏳ REVISIT**

> **Status: needs revisit.** Findings captured below from the investigation; a concrete
> decision (whether to add a first-class AG-UI client span) and any implementation are deferred.

## Summary
The reporter wraps a server-side `agent` with `UseOpenTelemetry` and hosts it via
`MapAGUI("/", agent)`, then drives it through `AGUIChatClient`/`AsAIAgent`. The agent's OTel is
emitted on **direct** invocation but **not** when invoked **through AGUI** (`Activity.Current`
is null inside the agent in the AGUI path). See the issue comments for the decorator-chain analysis.

## Findings

1. **Our hosting does not host `AIAgent`s.** `AGUI.Hosting.AspNetCore` has no `MapAGUI`, no
   `AIAgent`, and no `ActivitySource`/`Activity.` usage. It is **`IChatClient`-based**: each
   endpoint runs `chatClient.GetStreamingResponseAsync(...).AsAGUIEventStreamAsync(...)` inside
   the ASP.NET request. The reporter's **agent-level** OTel decorator + `MapAGUI(agent)` is
   **MAF-specific architecture** (MAF hosts agents; we host chat clients).

2. **An OTel-wrapped `IChatClient` flows through our hosting naturally** — we invoke it inside
   the request's Activity and suppress nothing, so chat-level spans are emitted server-side.

3. **Root cause is largely distributed-tracing semantics: telemetry is process-local.** Direct
   invocation runs the agent in the *client* process (which has the `TracerProvider`/exporter);
   through AGUI the agent runs in the *server* process, whose spans require **server-side** OTel
   config (`AddSource` + exporter). The reporter's server snippet configures no exporter, so
   nothing samples the source server-side → `Activity.Current` is null.

4. **Client→server trace context already propagates** on our client: `new AGUIChatClient(new(), url)`
   uses a plain `HttpClient`, whose built-in diagnostics auto-injects `traceparent` under an
   ambient Activity. `AGUIHttpTransport` builds a bare request and does not *explicitly* inject
   context, so this is handler-dependent but works with the default `HttpClient`.

## Open question to revisit
Should `AGUIChatClient`/`AGUIHttpTransport` emit their **own** first-class AG-UI client span
(an `invoke_agent`-equivalent for the proxy hop) and explicitly inject W3C trace context, rather
than relying on the ambient `HttpClient` behavior? This is an **enhancement**, not the reporter's
actual blocker (which is server-side OTel config + MAF agent hosting).

## Validation
No isolated unit test (asserting "a span exists" is fragile — depends on listener/exporter and
handler chain). Realistic validation, if we add an explicit client span, is an integration test
with an in-memory OTel exporter asserting the span + a propagated `traceparent` header.

## Proposed step (deferred — see REVISIT)
**Action item: add a sample that demonstrates OTel working end-to-end through AG-UI** — a
server that configures OpenTelemetry (`TracerProvider` + exporter + `AddSource`) and hosts an
instrumented chat client/agent, and a client that drives it through `AGUIChatClient` under an
ambient Activity, showing the server-side spans are produced and the `traceparent` links the
client and server traces. The sample doubles as the documentation that server-side telemetry is
**process-local** (must be configured on the server) and is propagated out-of-band, not via the
event stream. Separately, decide whether to add a first-class AG-UI client span.
