# Issue #3790 — AG-UI hosting drops FinishReason on RunFinishedEvent

- Repo: microsoft/agent-framework · [issue #3790](https://github.com/microsoft/agent-framework/issues/3790)
- Category: **Integration-pkg — by design (covered by interrupts); `finishReason` is non-protocol**

## Summary
The reporter wants `RunFinishedEvent` to carry `finishReason: "tool_calls"` so a client (TanStack
AI) executes client-side tools. Our hosting emits `RunFinishedEvent` with a plain success
outcome and does not propagate `ChatResponseUpdate.FinishReason`.

## Protocol check
`finishReason` is **not** part of the AG-UI protocol. `RunFinishedEvent` defines `threadId`,
`runId`, `result` (optional `any`), and `outcome` (`success`/`interrupt`) — see
`sdks/typescript/packages/core/src/events.ts:238` and
`src/AGUI.Abstractions/Events/RunFinishedEvent.cs`. The TanStack client's reliance on a
`finishReason` field is an OpenAI-style convention, not an AG-UI concept.

## Conclusion — covered by interrupts + transparent tools (not a gap)
AG-UI expresses *"the run is ending and the client must act"* natively, two ways — both already
supported by our SDK — so a `finishReason` field is unnecessary and would diverge from the spec:
1. **Transparent frontend-tool execution** — the agent emits `TOOL_CALL_*`, the run finishes
   `success`, and the client executes the tools it owns and continues. Validated by the
   cross-language mixed-tool test (`tests/CrossLanguage.Vitest/tests/mixed-tool-invocation.test.ts`).
2. **Tool-bound interrupt** ([AG-UI interrupts](https://docs.ag-ui.com/concepts/interrupts)) —
   for a tool call *awaiting a decision*, the run finishes with
   `outcome: { type: "interrupt", interrupts: [{ reason: "tool_call", toolCallId }] }`, and the
   client resolves via `resume`. This is our tool-approval pipeline (`RunFinishedInterruptOutcome`,
   Step09), covered by `tests/AGUI.Hosting.AspNetCore.UnitTests/InterruptContentTests.cs` and
   `MixedToolInvocationTest.cs`.

## Snippet — native tool-bound interrupt (when a decision is required)
Transparent frontend tools need no special server code (emit the tool call normally; the client
executes the tools it owns). When the tool call instead *awaits a decision*, emit a tool-bound
interrupt outcome — normally produced by our tool-approval pipeline (Step09), shown here for
illustration:
```csharp
yield return new ChatResponseUpdate
{
    RawRepresentation = new RunFinishedEvent
    {
        ThreadId = threadId,
        RunId = runId,
        Outcome = new RunFinishedInterruptOutcome
        {
            Interrupts = [new AGUIInterrupt { Id = id, Reason = "tool_call", ToolCallId = toolCallId }],
        },
    },
};
```

## Validation
By design — no dedicated test (per our rule). The native interrupt mechanism is covered by
`tests/AGUI.Hosting.AspNetCore.UnitTests/InterruptContentTests.cs`, `MixedToolInvocationTest.cs`,
and the cross-language mixed-tool test; the transparent path by the cross-language mixed-tool test.

## Proposed step
No framework change; do **not** add a `finishReason` field. Document that AG-UI clients drive
tool execution from `TOOL_CALL_*` events (transparent frontend tools) and the interrupt outcome
(tool-bound decisions), not `finishReason`.
