# Issue #6479 — Frontend tools break persisted chat history

- Repo: microsoft/agent-framework · [issue #6479](https://github.com/microsoft/agent-framework/issues/6479)
- Category: **AF-specific (persistence/history) — our stance: never synthesize; drop or throw**

## Summary
When a frontend (client) tool is invoked, the assistant turn contains a `FunctionCallContent`
the **client** resolves (it renders the tool). If the matching `FunctionResultContent` never
returns (page refresh, tab close, network drop, crash), any history that retains the dangling
call becomes unreplayable — the LLM rejects it with `400 ... No tool output found for function
call`.

## The reported bug is AF-specific (persistence we don't own)
The MAF triage pinpoints the root cause in MAF's **persistence layer**: `ChatClientAgent` +
`InMemoryChatHistoryProvider.StoreChatHistoryAsync` + `MapAGUI(agent)` saving the session
persist **all** response messages indiscriminately, including a frontend-tool
`FunctionCallContent` with no matching result; the next turn reloads the invalid history.

Our SDK owns **none** of that machinery — there is no `ChatHistoryProvider`, session store, or
server-side persistence in `src` (only a `StateCapabilities` flag). We are **stateless**: the
client sends the full history each turn (`RunAgentInput.messages`). So the bug *as reported*
(server persists a dangling frontend call to Cosmos) **cannot occur in our SDK**.

## This generalizes beyond frontend tools — it is a history-validity concern AF must own
The dangling call is not specific to AG-UI frontend tools: **any function represented only as a
declaration** (an `AIFunctionDeclaration` with no local implementation) can produce a
`FunctionCallContent` that never gets a result. Keeping a valid, replayable history in the
presence of such calls is therefore a responsibility of **AF's history/persistence layer**, not
of the AG-UI mapping. This needs to be validated with the AF team.

## Our stance / what is in our domain
We must **never synthesize a new message** (no placeholder `FunctionResultContent`) — fabricating
turns is not acceptable. In our stateless inbound path, if a client sends turn-2 history
containing a frontend `FunctionCallContent` with no matching result, the correct handling is to
**drop the dangling, unresolved client-tool call** when reconstructing the history (so it stays
LLM-valid), with **throwing a clear error** as an alternative option. Today `AsChatMessages`
maps history 1:1 with no such handling, so a dangling client-tool call would pass straight
through. Frontend-tool *surfacing* itself is correct (approval-wrapping in
`AGUIChatClient.cs:291-326` and `RunAgentInputExtensions.cs:49-54`); only the *resilience to a
missing result* is unaddressed.

## Validation
No test added yet (investigate mode). If we implement drop-or-throw, validate with a unit test:
feed inbound history with a client-tool `FunctionCallContent` but no matching
`FunctionResultContent` → assert the reconstructed `ChatMessage` list is LLM-valid (dangling
call dropped) or that a clear exception is thrown.

## Proposed step (not implemented — validate with AF)
1. Headline bug: **AF-specific** — AF's history/persistence layer must keep history replayable
   when a declaration-only function call has no result (generalizes beyond frontend tools).
2. Our part: decide **drop vs. throw** for an unresolved client-tool `FunctionCallContent` on the
   inbound reconstruction path — **never synthesize**. Validate the exact contract with AF first.
