# Issue #2179 — Allow MapAGUI to accept an agent name

- Repo: microsoft/agent-framework · [issue #2179](https://github.com/microsoft/agent-framework/issues/2179)
- Category: **AF-specific** — proposal for once MAF consumes our packages

## Summary

The issue asks for a `MapAGUI` overload that accepts an agent name/key string instead of requiring a pre-resolved `AIAgent` instance. This would let MAF resolve registered agents by name from DI when mapping the endpoint.

## What our packages already provide

The SDK exposes the protocol and conversion pieces needed by any MAF endpoint overload. `RunAgentInput` is public (`src\AGUI.Abstractions\Context\RunAgentInput.cs:11`-`17`), `ToChatRequestContext(...)` converts it into messages and `ChatOptions` (`src\AGUI.Hosting.AspNetCore\RunAgentInputExtensions.cs:40`-`49`, `src\AGUI.Hosting.AspNetCore\RunAgentInputExtensions.cs:91`-`108`), and `AsAGUIEventStreamAsync(...)` converts the returned MEAI stream to AG-UI events (`src\AGUI.Hosting.AspNetCore\ChatResponseUpdateAGUIExtensions.cs:29`-`39`).

## What remains MAF-side

Named/keyed agent registration and resolution are MAF DI concerns. Our packages intentionally do not know MAF's `AddAIAgent` key conventions, `IHostedAgentBuilder` names, endpoint overload design, or behavior when a key cannot be resolved.

## Proposal (once MAF consumes our packages)

1. Add a MAF overload like `MapAGUI(this IEndpointRouteBuilder endpoints, string pattern, string agentName)`.
2. Resolve the keyed `AIAgent` from `HttpContext.RequestServices` inside the endpoint delegate so DI scopes and late registrations behave consistently.
3. Reuse the same MAF internal helper as the `AIAgent` overload: bind `RunAgentInput`, call `ToChatRequestContext(...)`, invoke the resolved agent with `ctx.Messages`/`ctx.ChatOptions`, and stream `AsAGUIEventStreamAsync(...)`.
4. Consider implementing this overload as a thin wrapper over the more general factory overload proposed for issue #2988.
