# Issue #2702 — AG-UI with OpenAI Responses API stateful agents

- Repo: microsoft/agent-framework · [issue #2702](https://github.com/microsoft/agent-framework/issues/2702)
- Category: **AF-specific** — proposal for once MAF consumes our packages

## Summary

The issue reports that AG-UI `threadId` handling does not match stateful OpenAI Responses API agents, where each turn must use the latest `responseId` as the previous-response pointer. Keeping one AG-UI thread id for the whole conversation causes the backend to lose response-history continuity unless users add custom middleware that maps AG-UI thread ids to response ids.

## What our packages already provide

The protocol exposes `RunAgentInput.ThreadId` (`src\AGUI.Abstractions\Context\RunAgentInput.cs:13`-`17`) and `RunFinishedEvent.ThreadId` (`src\AGUI.Abstractions\Events\RunFinishedEvent.cs:12`-`16`). The default stream converter intentionally uses the incoming `context.Input.ThreadId` for automatic run lifecycle events (`src\AGUI.Hosting.AspNetCore\ChatResponseUpdateAGUIExtensions.cs:43`-`44`, `src\AGUI.Hosting.AspNetCore\ChatResponseUpdateAGUIExtensions.cs:376`-`380`). If MAF needs to override lifecycle events, any `BaseEvent` placed in `ChatResponseUpdate.RawRepresentation` is emitted directly (`src\AGUI.Hosting.AspNetCore\ChatResponseUpdateAGUIExtensions.cs:65`-`83`).

## What remains MAF-side

Mapping OpenAI Responses `responseId` values to AG-UI threads is session-store / agent-thread behavior owned by MAF and the OpenAI Responses integration. Our SDK does not know which providers require a previous-response id, when a response id is durable, or where MAF wants to persist that mapping.

## Proposal (once MAF consumes our packages)

1. In MAF's OpenAI Responses agent adapter, read the original AG-UI request from `ctx.Input.ThreadId` or `ChatOptions.AdditionalProperties[AGUIConstants.RunAgentInputKey]` and resolve the latest stored `responseId` for that logical AG-UI thread.
2. Pass that response id to the OpenAI Responses API as the previous response/thread value for the next turn, while preserving the client-visible AG-UI thread unless MAF intentionally supports thread migration.
3. Persist the newly returned `ChatResponseUpdate.ResponseId` into MAF's session/thread store at the end of each run.
4. If MAF chooses to change the client-visible AG-UI thread to the new response id, emit an explicit `RunFinishedEvent` via `ChatResponseUpdate.RawRepresentation` so the SDK does not generate the default event with the old `context.Input.ThreadId`.
